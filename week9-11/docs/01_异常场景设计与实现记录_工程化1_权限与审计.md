## 二、至少两类角色（按数据库既有定义）

数据库 `role` 表要求 `role_code` 以 `ROLE_` 开头，已有三个角色：

| role_id | role_code | 角色名 | 权限边界 |
| --- | --- | --- | --- |
| 1 | `ROLE_USER` | 普通用户 | 只读会议室、提交/取消**自己的**预约、上报故障、查看**自己的**操作记录 |
| 2 | `ROLE_ROOM_ADMIN` | 会议室管理员 | 管理会议室与设备、审核预约、处理故障、查看**本会议室**审计日志 |
| 3 | `ROLE_SYS_ADMIN` | 系统管理员 | 用户与角色管理、全量审计日志、数据导出、人脸库治理（删改） |

`user_role` 为复合主键（`user_id + role_id`），支持一人多角色；登录返回的 `UserLoginVo{id, username, isAdmin, loginAccount, token}` 里 `isAdmin` 只用于前端菜单，**不能作为权限依据**（这是要修的点：以服务端 `@PreAuthorize` 为准）。

## 三、系统怎样提示（三端一致）

| 场景 | 后端响应 | 前端表现 |
| --- | --- | --- |
| 未登录 / token 失效 | HTTP 401，`{"code":0,"msg":"未登录或登录已过期"}` | 跳 `/login`，登录后回原路径 |
| 已登录但无权限 | HTTP 403，`{"code":0,"msg":"没有操作权限，请联系管理员"}`（复用 `GlobalExceptionHandler` 的 `AccessDeniedException` 分支） | 顶部红色 Toast + 按钮置灰，不弹全屏遮罩 |
| 越权调用管理接口（直接改 URL） | 403 + 审计日志 `operation_result=fail, error_msg=AccessDenied` | 同上；页面停留在原页 |
| 人脸注册被拒 | 403 `{"enrolled":false,"error":"无权限注册该身份"}` | 明确文案「该人脸已绑定其他账号，如需变更请联系管理员」 |

**不做**：把“无权限”笼统提示成“系统错误”，那样用户会反复重试。

## 四、日志怎样记录（operation_log 落地）

### 4.1 表结构（已存在，直接使用，不改字段）

`id / log_no / user_id / user_name / operation_type / operation_content / operation_result / operation_time / ip_address / user_agent / error_msg`

### 4.2 实现方式：注解 + AOP 切面

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    String type();          // 例如 USER_MANAGE / RESERVATION_AUDIT / FACE_ENROLL
    String content() default "";
}

@Aspect
@Component
public class AuditLogAspect {
    @Around("@annotation(auditLog)")
    public Object around(ProceedingJoinPoint pjp, AuditLog auditLog) throws Throwable {
        long t0 = System.currentTimeMillis();
        String result = "success", err = null;
        try {
            return pjp.proceed();
        } catch (Throwable ex) {
            result = "fail";
            err = ex.getMessage();
            throw ex;
        } finally {
            OperationLog log = new OperationLog();
            log.setLogNo("OP" + DateTimeFormatter.ofPattern("yyyyMMddHHmmssSSS").format(LocalDateTime.now())
                         + ThreadLocalRandom.current().nextInt(100, 999));
            log.setUserId(currentUserId());
            log.setUserName(currentUserName());
            log.setOperationType(auditLog.type());
            log.setOperationContent(auditLog.content() + " 参数=" + safeArgs(pjp));
            log.setOperationResult(result);
            log.setOperationTime(LocalDateTime.now());
            log.setIpAddress(RequestContext.getIp());
            log.setUserAgent(RequestContext.getUa());
            log.setErrorMsg(err);
            auditLogService.saveAsync(log);   // 异步，不阻塞业务
        }
    }
}
```

使用示例：

```java
@AuditLog(type = "USER_DELETE", content = "删除用户")
@DeleteMapping("/admin/user")
@PreAuthorize("hasRole('ROLE_SYS_ADMIN')")
public Result deleteUser(@RequestParam Long id) { ... }
```

### 4.3 记录规则（写清才叫“日志怎样记录”）

| 规则 | 内容 |
| --- | --- |
| 记录范围 | 所有管理端写操作 + 人脸注册/删除 + 登录失败 + 越权拒绝 |
| 敏感字段脱敏 | 参数中的 `password`、`token`、`image`（base64）一律替换成 `***`；只记身份标识与外键 id |
| 结果必记 | 成功与失败都写，`operation_result` 取 `success`/`fail`，失败填 `error_msg` |
| 写入方式 | 异步线程池（`@Async`），失败时降级写本地 `logs/operation_fallback.log`，不影响主流程 |
| 保留与防删 | 应用账号只授予 `INSERT/SELECT`，不授予 `DELETE/UPDATE`（DDL 层保护）；按月归档 |
| 可追溯性 | `log_no` 唯一，前端审计页可按 `user_id / operation_type / 时间范围` 过滤 |

### 4.4 查看入口

`GET /admin/audit/page?page&pageSize&operationType&userId&start&end`，仅 `ROLE_SYS_ADMIN` 可调用；`ROLE_ROOM_ADMIN` 只返回 `operation_type` 属于会议室管理、且 `content` 命中本会议室 id 的记录。

## 五、人脸数据与日志数据的访问矩阵（任务书明确要求）

### 5.1 人脸数据

| 数据 | 数据主体本人 | ROLE_USER | ROLE_ROOM_ADMIN | ROLE_SYS_ADMIN | 说明 |
| --- | --- | --- | --- | --- | --- |
| 人脸原图（`id/<identity>.jpg`） | 可查看自己的（仅确认“已注册”，不提供下载） | 不可见他人 | 不可见 | **可删改**（需二次确认 + 审计） | 原图不出网络、不提供批量导出 |
| 人脸特征/比对结果 | 可查看自己的最近一次比对结论 | 只能查询本人 | 不可查询他人 | 可查全量 | 比对结果只回 `matched/identity/threshold`，不回 distance 以外信息 |
| 注册/删除动作 | 仅本人可发起（且需登录态） | 不可代注册 | 不可 | 可强制删除 | 动作全量写审计日志 |
| 门禁通行记录 | 可查自己的 | 仅本人 | 会议室级汇总（不含身份） | 全量 | 汇总只给次数，不给明细 |

配套整改：
1. `/api/face/enroll` 必须携带用户 token（或一次性注册码），`identity` 必须等于登录账号，**禁止代注册**；
2. `/api/face/verify` 只允许来自内网/门禁终端，加 IP 白名单 + 限流（每分钟 ≤ 20 次）；
3. `/health` 去掉 `db_path`，只返回 `status/model/threshold`；
4. 人脸目录权限收紧（Linux `chmod 700`，仅服务账号可读）；日志与备份不同机存放。

## 六、怎样恢复或处理（异常处置流程）

| 异常 | 处置动作 | 恢复方式 |
| --- | --- | --- |
| 用户被误判无权限 | 审计页按 `user_id` 查最近 10 条，核对角色绑定 | 由 `ROLE_SYS_ADMIN` 在用户管理页补授角色，**下一次请求即生效**（权限从 `user_role` 实时读，不缓存） |
| 有人尝试越权 | 403 + 审计记录（含 IP/UA） | 连续 5 次 403 自动锁该账号 15 分钟（`Redis` 计数），管理员解锁 |
| 审计写入失败 | 业务不回滚，降级本地文件 | 后台补偿任务每 5 分钟重放 `operation_fallback.log` |
| 人脸被冒名注册 | 告警 + 冻结该 identity | 管理员删除旧图 → 本人重新注册（旧图进回收站 7 天可溯源） |
| 日志被误删 | — | 每日 `mysqldump` 备份，可按天恢复；生产账号无 DELETE 权限，从机制上避免 |
