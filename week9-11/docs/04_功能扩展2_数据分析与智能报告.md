# 功能扩展 2：数据分析与智能报告

> 同样必须“从界面或接口实际可用”。本项**已经部分可直接运行**：仓库自带 `/api/history`、`/api/export/csv`、`/chart/*` 与 `/admin/statistics/近7天`，我们在此基础上做“指标定义 + 报告生成 + 页面呈现”，不写独立演示脚本。

## 一、为什么做

1. 现在有数据、没结论：传感器服务每 3 s 记一条，`/api/history` 最多 120 点，`/api/export/csv` 能导 CSV（实测 11,059 字节、15 列中文表头），但**没有任何“这周会议室用得怎么样”的计算**；
2. 管理端 `StatisticsVo{dailyData, totalUsageCount, totalFaultCount, faultHandleRate}` 已定义、`/admin/statistics/近7天` 已有路由，但前端只有零散图表，缺一份“能交上去”的周报；
3. 答辩/验收场景：评审更愿意看“指标 + 趋势 + 异常点”，而不是裸曲线。

## 二、怎样实现

### 2.1 指标口径（先定义，再算）

| 指标 | 公式 | 数据来源 | 说明 |
| --- | --- | --- | --- |
| 会议室使用率 | 已预约时长 / 可预约时长（08:00-20:00 × 天数） | `reservation`（status 0/1/3） | 取消（status=2）不计入 |
| 单场平均时长 | 已结束预约时长 / 场次数 | 同上 | 反映会议碎片化程度 |
| 环境超标次数 | `temperature > temp_max + 1` 或 `humidity > humidity_max` 的样本数 | `/api/history` + 接口下发阈值 | **阈值必须读接口字段**，不能硬编码（对应 D-06） |
| 烟雾报警次数 | `smoke >= 100`（后端阈值）样本数 | 同上 | 与 `alarm` 输出口径一致（D-04） |
| 门禁开启次数/时长 | `door_open=true` 的样本数与连续段时长 | 同上 | 用于“长开门”提醒 |
| 故障处理率 | 已处理故障 / 总故障 | `device_fault` + `StatisticsVo.faultHandleRate` | 管理端已有字段，直接复用 |
| 离线率 | 断连时长 / 统计周期 | 第 9 周心跳日志 | 反映服务稳定性 |

### 2.2 后端（新增两个接口，不动 v1.0 既有字段）

```
GET /api/report/daily?date=2026-11-08        # 传感器侧：环境日报
GET /admin/report/weekly?start=2026-11-02&end=2026-11-08   # 业务侧：会议室周报
```

日报返回：

```json
{"date":"2026-11-08","samples":114,"temp":{"avg":24.8,"min":23.1,"max":27.4},
 "temp_over_limit":3,"humidity_over_limit":0,"smoke_alerts":0,
 "presence_ratio":0.42,"door_open_minutes":18,"availability_pct":100.0,
 "conclusion":"当日环境整体正常，10:12-10:15 温度超上限 1.4℃，建议检查空调"}
```

`conclusion` 由规则生成（不是大模型）：命中“超标/报警/离线/长开门”任一规则就输出对应句子，全部正常则输出“无异常”。**规则可追溯**，答辩时能逐条解释。

周报（Markdown）结构：

```
# 会议室周报 2026-11-02 ~ 2026-11-08
## 一、总体
- 总预约场次 / 总使用时长 / 平均时长 / 使用率
## 二、分房间
| 房间 | 场次 | 时长 | 使用率 | 故障数 | 处理率 |
## 三、环境与安全
- 温度超标 x 次（最高 27.4℃ @ 10:12）
- 烟雾报警 0 次；门禁长开 2 次（最长 12 分钟）
## 四、异常与建议
1. 302 房间 3 次故障均未在 24h 内处理 → 建议指派
2. 301 使用率 12% 偏低 → 建议调整开放时段
```

### 2.3 前端（新增「数据报告」页 `/report`）

- 顶部 4 张指标卡：使用率、平均时长、故障处理率、离线率；
- 中部两张图：近 7 天使用时长柱状图、温湿度折线（带阈值参考线，阈值取自接口）；
- 底部「生成本周报告」按钮 → 调 `weekly` → 页面内预览 Markdown → 「下载 .md」/「复制」；
- 空数据保护：`/api/history` 为空时显示「暂无数据，请先启动传感器服务」，不显示 0 值假图表。

### 2.4 复用而非重造

| 已有能力 | 本项如何用 |
| --- | --- |
| `/api/history`（120 点） | 环境指标计算源；不足一天时报告标注“样本不足” |
| `/api/export/csv`（15 列） | 「下载原始数据」按钮，报告页脚注明数据可回溯 |
| `/chart/temp_humidity`、`/chart/sensor` | 页面缩略图直接引用，少写一套绘图代码 |
| `StatisticsVo` / `/admin/statistics/近7天` | 周报的一、二节直接取该接口的 `dailyData` |

## 三、怎样测试

| 用例 | 场景 | 期望 |
| --- | --- | --- |
| TC-41 | 正常数据（114 样本） | 日报 `samples=114`，`availability_pct=100`，`conclusion` 含“无异常”或具体超标描述 |
| TC-42 | 构造温度 30℃（>26+1） | `temp_over_limit>0`，`conclusion` 含“温度超上限” |
| TC-43 | 构造 smoke=180 | `smoke_alerts>0`，`conclusion` 含“烟雾报警” |
| TC-44 | `/api/history` 为空 | 日报返回 `samples=0` 且 `conclusion="样本不足"`，前端不渲染假图表 |
| TC-45 | 周报 7 天无预约 | 使用率 0%，报告仍能生成，注明“本周无预约” |
| TC-46 | 报告 Markdown 中数字 | 与 CSV 原始数据抽样核对一致（抽 5 个点） |
| TC-47 | 连续生成 10 次 | 结果一致（同一输入同输出），P95 ≤ 200 ms |

**当前状态**：日报/周报接口**尚未落库实现**；可运行的替代验证是 `scripts/api_contract_test.py` 已覆盖 `/api/history`、`/api/export/csv`、`/chart/temp_humidity`（TC-04/05/18 均通过），证明数据源可用。TC-41—TC-47 在有数据后执行并回填。

## 四、为什么算“功能扩展”而不是“演示脚本”

1. 有独立路由与页面入口（`/report`），用户能点进去看到自己会议室的数据；
2. 指标来自真实接口与数据库，不是写死的 JSON；
3. 输出物可交付（.md 周报 + CSV 原始数据），管理端能直接用于周会。
