# 功能扩展 1：多会议室智能调度

> 第 10 周要求：功能扩展累计至少 2 项，且必须“从界面或接口实际可用”，不能说“有个独立演示脚本”。每项写清**为什么做、怎样实现、怎样测试**。
> 本项落在现有预约链路上（`/user/reservation/slots` → `/user/reservation`），不是外挂脚本。

## 一、为什么做

1. 现状痛点：用户预约时只能自己翻房间、自己比时段。`/user/reservation/slots` 只回答“这个房间这天哪些时段可约”（`TimeSlotVo.status`：0 可约 / 1 占用 / 2 过期），**不回答“我这场会该订哪个房间”**；
2. 数据已经齐了但没被用起来：`meeting_room` 有 `capacity`、`location`、`equipment`、`status(0空闲/1占用/2维修/3已预约未使用)`、`is_active`；`reservation` 有 `start_time/end_time/status`，且有 `idx_reservation_room_time` 索引可直接做冲突查询；
3. 目标：给一个“会议需求”就能拿到 3 个候选房间 + 可约时段 + 推荐理由，减少反复试错和“订了大房间只来 3 个人”的浪费。

## 二、怎样实现

### 2.1 接口（新增，v1.0 向后兼容，不改既有字段）

```
POST /user/reservation/recommend
Content-Type: application/json

{
  "startTime": "2026-11-10 09:00:00",
  "endTime":   "2026-11-10 10:30:00",
  "participantNum": 8,
  "equipment": ["投影", "白板"],
  "preferLocation": "3楼"
}
```

返回：

```json
{
  "code": 1,
  "data": {
    "recommendations": [
      {"roomId": 2, "roomCode": "302", "location": "3楼东区", "capacity": 12,
       "score": 92.5, "available": true,
       "reasons": ["容量匹配(8/12)", "设备齐全(投影+白板)", "该时段空闲", "近30天使用率偏低，优先均衡"]},
      {"roomId": 1, "roomCode": "301", "capacity": 24, "score": 78.0, ...}
    ],
    "excluded": [{"roomId": 3, "reason": "维修中"}, {"roomId": 5, "reason": "时段冲突 09:00-10:00"}]
  },
  "msg": "ok"
}
```

### 2.2 算法（硬约束过滤 + 软评分排序）

**硬约束（不满足直接排除，并给出原因）**

| # | 条件 | 实现 |
| --- | --- | --- |
| 1 | 房间启用 | `meeting_room.is_active = 1` |
| 2 | 非维修 | `status != 2` |
| 3 | 容量够 | `capacity >= participantNum` |
| 4 | 时段不冲突 | `SELECT COUNT(*) FROM reservation WHERE room_id=? AND status IN (0,1,3) AND start_time < #{end} AND end_time > #{start}`（利用 `idx_reservation_room_time`） |
| 5 | 设备满足 | `equipment` 字段按 `+`/`、` 分隔后包含全部所需项（缺失项即便排除也写进原因，便于用户放宽） |

**软评分（0-100，权重写在配置里便于调整）**

| 维度 | 公式 | 权重 |
| --- | --- | --- |
| 容量匹配 | `100 * (1 - (capacity - participantNum) / capacity)`，不足 1 人按 1 计 | 0.35 |
| 设备完整度 | 命中设备数 / 需求设备数 * 100（无需求记 100） | 0.20 |
| 位置偏好 | 命中楼层 100，同楼不同区 70，其它 40 | 0.15 |
| 时段宽松度 | 该房间当天剩余可约时段数 / 最大可约时段数 * 100 | 0.10 |
| 使用率均衡 | `100 * (1 - 近30天该房间已预约小时 / 最长房间已预约小时)` | 0.20 |

`score = Σ(维度分 * 权重)`，取 Top 3；分数相同按 `capacity` 升序（更省空间）。

### 2.3 前端（`booking` 页）

- 新增「智能推荐」按钮：取当前表单的日期/时段/人数/设备，调 `recommend`；
- 结果以 3 张卡片展示：房间号 + 容量 + 匹配分 + 3 条理由 + 「选它」按钮；
- 点「选它」自动填 `roomId` 并调用既有 `/user/reservation/slots` 二次确认，再走原提交接口——**复用原有提交链路，不新建一套预约逻辑**；
- 被排除房间折叠展示（“3 间不满足，展开看原因”），避免用户以为“没房间”。

### 2.4 数据一致性

- 推荐结果**不落库**，实时计算（3 个房间的规模毫秒级）；
- 提交时后端仍要再校验一次冲突（`ck_time_order` + 业务校验），防止“推荐时可用、提交时被抢”；
- 并发冲突：提交接口用 `SELECT ... FOR UPDATE` 锁定该房间当日记录，冲突则返回 `code=0, msg="该时段已被占用，请重试"`。

## 三、怎样测试

| 用例 | 输入 | 期望 | 类型 |
| --- | --- | --- | --- |
| TC-35 | 8 人、需投影+白板、09:00-10:30 | 返回 ≥1 个 `available=true` 且 `capacity>=8`，Top1 分数最高 | 正向 |
| TC-36 | 30 人（超过所有房间容量） | `recommendations` 为空，`excluded` 每间都有“容量不足”原因 | 边界 |
| TC-37 | 与已存在预约重叠 09:00-10:00 | 该房间进 `excluded`，原因含“时段冲突” | 冲突 |
| TC-38 | 房间 `status=2`（维修） | 该房间被排除，原因“维修中” | 状态 |
| TC-39 | 提交已被抢的时段 | `code=0`，提示“该时段已被占用，请重试”，不产生重复记录 | 并发 |
| TC-40 | 同一输入连续调用 10 次 | 结果稳定（分数一致），响应 P95 ≤ 50 ms | 稳定性 |

执行方式：`curl` 打 3 个房间的真实数据；并发用 `scripts/performance_test.py` 同款线程池改写路径即可复用。
