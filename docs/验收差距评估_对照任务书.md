# 综III 项目验收差距评估（对照《课题任务书 V3.0》）

- **评估对象**：`Intelligent-Meeting-Cloud-main`（综III 12 周交付包）
- **评估依据**：《2026-2027-1 学期进阶式挑战性综合项目 III 课题任务书 V3.0 — 树莓派智能会议室管理系统》
- **评估方式**：逐条读任务书条款 → 在仓库中找代码/数据/日志/截图证据 → 本机实跑复核 + 独立复算数据
- **评估日期**：2026-11-13

## 0. 一句话结论

**不圆满。按任务书「六个必做块」的「必须」口径，没有一块能完整打钩。**

- **形式齐备但实质打折 2 项**：数据分析（来源虚报 + 循环论证 + 「Web/3D 可见」陈述失实）、工程化（只有「测试与性能」一项完整达标）
- **部分达标 2 项**：接手跑通链路（模拟端实跑通，全栈未验收、无 Git）、测试与材料（52 条用例真，但口径矛盾、缺陷未真闭环）
- **未达标 1 项**：3D 场景改进（任务书写「**必须**用 Blender 或 Unity」，仓库无任何 Blender 生产物）
- **申报错位 1 项**：功能扩展——申报的两项（智能调度、智能报告）代码里不存在，但客观另有 2 项有代码的扩展（设备控制闭环、自然语言预约助手）没被申报；改口径 + 补测试即可救回
- **人脸识别**：两块自研算法代码真实可信，但**真实样本 0 张、真实 FAR/FRR/Pi 时延全「待实测」、自研链路未接入业务** → 按任务书「半自主开发最低判断标准」**不算完成**
- **交付物**：缺中期/总结报告、缺五角色分工与个人贡献证据、演示视频 0 个、Git 仓库与提交记录缺、Python 依赖清单缺
- **最大风险**：答辩 PPT 把 Blender、Spring/MySQL 联调、实物硬件、扩展接口、预录视频五类「未验收/未实现」内容讲成了已交付，与仓库自己的《验收指标表》《delivery/README》正面冲突

**三处必须改的实质问题**

1. **数据来源虚报**。数据由 `week3/scripts/generate_raw_data.py`（`random.seed(20260901)`）按 28 天 × 3 室 × 5 min 造出 14112 条，占用状态由硬编码时段概率决定（9-11 时 p=0.85、14-17 时 p=0.80、周末 p=0.08），再注入 236 条脏数据。但 `data_quality_report.md:13` 写「数据来源：本组综II…导出的原始数据」，`week4_analysis_report.md` 全程未披露合成。任务书明确要求「说清楚数据从哪里来」。
2. **指标是循环论证**。独立复算证明温度≈小时的线性函数（14 个整点与公式偏差全在 ±0.03 ℃ 内）、湿度与温度相关系数 −0.8422（与生成器 `uniform(−3.5,3.5)+uniform(−0.5,0.5)` 残差吻合）、distance 与 occupancy 近乎完全可分；分小时占用率与生成器 p 值逐小时偏差 ≤2.5 pp。所以「高峰 10:00 / 42.9%」是 p 值的复述，不是从真实行为里发现。501 室 accuracy=1.0000 正是「p=0.1275 恒判无人」的产物（报告 `week4_analysis_report.md:78` 自己承认）。
3. **「Web/3D 消费」陈述不成立**。`week4_analysis_report.md:83-86` 称基线结果「由 3D 与 Web 端按 occupancy/devices 消费」，但全仓 grep：`baseline_result` / `state_with_baseline` / `clean_data_v1` 的消费者只有 week4 自己的脚本和 md；`state_with_baseline.json` 里 `occupancy_predicted:true` 与同行 `occupancy:false` 自相矛盾；前端 `statistics.js` 默认走 `getStatisticsMock()`，`package.json` 无任何图表库，`router/index.js` 无 `/report` 路由。

**小缺陷**：注入 40 条重复只删了 39 条，`2026-09-10 19:15:00 / room 501` 仍残留两组（一组 humidity 为空躲过 subset 去重），所以 14113 比真实干净底稿 14112 多 1 条，`data_quality_report.md:68` 的前后对比差 1。

## 8. 结论

**按任务书的「必须」口径，本项目目前是一份「工程量大、证据量足、但两处必须项硬缺 + 一处申报错位」的半成品。**

硬缺（真做不了/没做）：
1. **Blender/Unity 环节**（任务书写「必须」）——无任何生产物（`.blend`、导出 glb、运行记录全无）
2. **人脸识别的真实测试 + 业务闭环**（任务书写「最低判断标准」）——真实样本 0 张、自研链路未接入

申报错位（有东西但申报错了）：
3. **功能扩展**——文档/PPT 申报的「智能调度」「智能报告」不存在，但设备控制闭环与自然语言预约助手是有的，重新申报即可

交付面硬缺：**中期/总结报告、五角色分工与个人贡献、演示视频、Git 仓库、Python 依赖清单**。

可补性判断：
- **只需现有条件就能补的**：功能扩展改口径 + 补测试记录（1 天）、人脸真人测试（半天）、总结报告与分工表（1 天）、演示视频（半天）、requirements.txt 与 Git（半天）、PPT 措辞与数据来源表述（半天）
- **需要外部环境的**：Blender 实际导出（装 Blender）、Spring/MySQL/Redis 联调（启 Redis + 腾端口 + 导库）、实物 Pi（现场网络）

建议的答辩策略：**主打能证明的（可复跑用例、可复现清洗与图表、Three.js 3D 工程质量、自研 LBP 代码、性能与心跳数据、诚实的边界声明），把 P2 项一律标注「未验收」**。这样即使 Blender 和全栈联调仍缺，也是一份「主体完成、边界如实」的可接受交付；反之若 PPT 继续把未做的讲成做了，一旦老师按编号追溯（`验收指标表` 就在仓库根目录），风险远大于收益。
