# 实时联动与刷新机制（轮询 / 推送判定 + 实测数据）

> 对应第 7 周要求：「至少一类状态做实时联动并录屏，写清刷新机制是轮询还是推送」。

## 一、结论先行

| 项 | 结论 |
| --- | --- |
| 刷新机制 | **前端主动轮询（pull / polling）**，不是长连接推送 |
| 轮询周期 | 3000 ms（`Room3D/index.vue:1040`） |
| 传输方式 | HTTP GET `/sensor-api/current` → Vite 代理 → Flask `GET /api/current` |
| 数据生产端 | 树莓派/本机 Flask 服务后台线程 `sensor_loop()` **每 3 s 采集一次**并写日志（`Flask/unified_meeting_room_system.py:613-640`） |
| 端到端延迟 | 实测中位数 15 ms（本机），最坏 ≈ 采集周期 3 s + 轮询周期 3 s ≈ 6 s |
| 是否够“实时” | 对本项目（人数/门/温湿度）够用；烟雾报警这类**安全信号偏慢**，见缺陷 D-03 建议 |

**为什么用轮询而不是 WebSocket/SSE：**

1. 传感器服务的生产端本身就是 3 s 采样一次（`sensor_loop` 内有 `time.sleep(3)`），推送频率不会比轮询更高，改为推送收益为零；
2. Flask 服务当前是无状态 REST + `threading.Lock` 保护共享变量，加 WebSocket 需要引入 `flask-socketio` 与事件循环，改动面大于收益；
3. 第 8 周冻结接口后第 9-11 周的工程化（心跳/重连/降级）在轮询模型下实现成本最低——**失败即“这次没拿到”，可直接在页面上表达断连**，而推送需要额外处理连接状态机。

## 二、链路（数据 → 后端 → 3D）

```
传感器 / 模拟采集线程  sensor_loop()  每 3 s
        │ 写全局变量（data_lock 保护）
        ▼
Flask  GET /api/current        返回 17 字段 JSON（Flask/unified_meeting_room_system.py:651-675）
        ▼
Vite   /sensor-api 代理        rewrite → /api（vite.config.js:40-44）
        ▼
axios  getCurrentSensorData()  超时 5000 ms（src/apis/sensor.js:3-15）
        ▼
Vue    refreshSensorData()     合并进 sensorData → 触发 roomState computed
        ▼
Three  updateSensorVisuals()   改对象属性：rotation / intensity / emissive / visible / scale
```

关键点：**刷新是「拉」不是「推」**，页面不会因为后端数据变化被动更新，必须等下一次 `setInterval` 触发。这也是验收「停掉后端仍显示正常内容」风险的技术根源（见第四节）。

## 三、实测数据（真实运行，非构造）

采集方式：本机启动 Flask 服务 + 前端 5173，脚本每 3 s 请求一次 `/api/current`，连续 10 次（`scripts/verify_state_binding.py` 同款逻辑）。

| 指标 | 实测值 | 证据 |
| --- | --- | --- |
| 采样间隔均值 | **3.01 s** | `results/轮询刷新实测.json` → `poll_gap_avg_s` |
| 相邻两次数据发生变化的次数 | **9 / 9** | 同上 → `poll_changed_pairs` |
| 变化字段 | `temperature` / `light` / `smoke` / `motion` / `door_open` 均有变化 | 同上 → `poll_samples` |
| `/api/current` 顺序请求 100 次 | 平均 14.25 ms，P95 16.05 ms | `results/接口冒烟结果.json` → `perf_sequential` |
| 20 线程 × 50 次并发 | 1000 次全部成功，0 错误，吞吐 1125.9 req/s，P95 28.88 ms | 同上 → `perf_concurrent` |

> 说明：并发数字来自本机 Flask 开发服务器（`app.run`，非生产 WSGI），仅用于证明“轮询不会压垮服务”，不代表线上容量。

## 四、失败与降级行为（真实现状，必须整改）

代码行为（`index.vue:890-893`）：

```js
} catch (error) {
  sensorState.value = 'demo';
  lastUpdated.value = '模拟数据';
}
```

- 请求失败时**不清空 `sensorData`**，仍用上一次的值 + 组件默认值继续渲染，只在右上角把「实时数据 13:48:47」改成「模拟数据」；
- 实测：**停掉 Flask 服务**后整页仍显示完整场景（25.0℃ / 50% / 无人 / 门关），见 `results/screenshots/3d_sensor_offline_1920x1080.png`；
- 风险：验收判据明确写「把后端停掉，场景还显示正常内容，就说明状态是写死的」。**本实现会被误判**，尽管实际是接口读取。
- 已登记缺陷 **D-02**，修复要求：断连时必须出现**显式红色横幅**「接口断开，数据不可用（最后成功：hh:mm:ss）」+ 场景降饱和置灰 + 控制按钮禁用，不允许“静默降级”。

## 五、录屏拍摄脚本（现场录制用，3 分钟内）

| 时间 | 操作 | 期望画面 |
| --- | --- | --- |
| 0:00-0:15 | 终端执行 `python Flask/unified_meeting_room_system.py`，再 `npm run dev` | 服务启动，日志每 3 s 打印一行采集记录 |
| 0:15-0:35 | 打开 `http://127.0.0.1:5173/room-3d`，指出右上角「实时数据 hh:mm:ss」 | 时间每 3 s 跳动 |
| 0:35-1:00 | 用 Postman/命令行 `POST /api/control` 开门、开灯 | 3 s 内门扇旋转打开、顶灯亮起、面板「门禁 已开启 / 照明 开启」 |
| 1:00-1:25 | 现场走动触发 PIR，或手动遮挡（真实树莓派） | 「人员 N人」变化，人形模型出现 |
| 1:25-1:50 | 用热水杯靠近 DHT11（真实设备）或调节温度 | 数值变化，空调模块变色 |
| 1:50-2:10 | **停掉 Flask 服务** | 页面出现「接口断开」横幅（修复后），当前为「模拟数据」提示 |
| 2:10-2:30 | 重启 Flask | 自动恢复「实时数据」 |
| 2:30-2:50 | 口头说明：轮询 3 s，非推送；失败迁移到本地预览 | 收尾 |

录制要求：录屏软件同时录到**终端日志窗口**和**浏览器**，画面里能看清 `timestamp` 与终端日志时间对齐（证明数据来自接口而非本地）。

## 六、复现命令

cd FrontEnd/Intelligent_meeting_cloud
npm install

# 3. 验证接口
Invoke-RestMethod http://127.0.0.1:5000/api/current

Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5000/api/control `

# 5. 轮询与状态校验
python week7-8/scripts/verify_state_binding.py --base http://127.0.0.1:5000
