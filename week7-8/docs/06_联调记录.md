## 三、链路时序（一次状态变化的完整传播）

```
T+0.0s   真实/模拟传感器更新（sensor_loop 每 3 s）
T+0.0s   写入全局 current_* 变量（data_lock 保护）
T+0.0s   GET /api/current 返回该快照（带 timestamp）
T+0~3s   前端 setInterval 到点 → axios GET /sensor-api/current（超时 5 s）
T+0.1s   refreshSensorData 合并 → roomState 重算
T+0.1s   updateSensorVisuals 改 Three.js 对象属性 → 下一帧 render
T+3.0s   下一次轮询（若数据未变，画面保持不变）
```

用户可感知的端到端延迟 ≤ 6 s（3 s 采集 + 3 s 轮询，最坏叠加）；本机实测请求耗时 14-16 ms，占比可忽略。

## 五、故障排查手册（现场遇到问题按此查）

| 现象 | 可能原因 | 排查命令/动作 |
| --- | --- | --- |
| 页面右上角一直「模拟数据」 | 5000 未启动 / 代理目标错 | `Invoke-RestMethod http://127.0.0.1:5000/api/current`；查 `vite.config.js` 的 `VITE_SENSOR_PROXY_TARGET` |
| 页面能开但 3D 黑屏 | WebGL 被禁用 / 显卡驱动 | `chrome://gpu` 看 WebGL；或加 `--enable-unsafe-swiftshader` 验证 |
| 数据不更新 | 轮询定时器被页面隐藏挂起（浏览器节流） / 服务 `sensor_loop` 停了 | 看 `data/unified_sensor_log.txt` 是否持续追加 |
| 门点了没反应 | 后端返回无 `door_open`（树莓派舵机不可用）→ 抛错后退回本地预览 | 看浏览器控制台 `Door servo endpoint is not available...`；确认真实舵机接线 GPIO13/12 |
| 控制后 3 s 才变 | 正常（轮询周期 3 s），非 bug | 说明刷新机制是轮询 |
| 中文日志乱码 | 终端编码非 UTF-8 | `chcp 65001` 后重启服务 |
| 端口被占 | 上一次服务未退出 | `Get-NetTCPConnection -LocalPort 5000`，必要时结束进程 |

## 六、联调结论

1. **闭环成立**：状态值全部来自 `/api/current`，控制指令经 `/api/control` 写回后由 3D 呈现，非前端自造数据；
2. **仍需整改**：断连态（D-02）与报警可见性（D-03）不满足任务书“异常有明显提示”的要求，第 8 周内完成，否则本节点的“交互与提示”一项不能判合格；
3. 业务后端（Spring Boot）未参与本次 3D 链路，第 9 周在具备 Maven/MySQL/Redis 的环境补齐业务侧联调，本轮不宣称其“已通过”。
