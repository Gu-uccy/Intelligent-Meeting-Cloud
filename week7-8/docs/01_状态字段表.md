# 状态字段表（接口字段 → 3D 对象属性映射）

> 对应第 7 周硬指标：「至少 3 类状态（人员、门、温湿度、设备）随数据变化更新，状态从接口读」；验收材料要求「状态字段表 + 联动录屏」。
> 本表按**仓库真实代码**逐字段核对，代码位置精确到文件行号，可直接对照验收。

## 一、数据来源与读取方式

| 项 | 内容 |
| --- | --- |
| 状态源接口 | `GET /api/current`（树莓派/本机 Flask 统一传感器服务，默认 `http://127.0.0.1:5000`） |
| 前端调用地址 | `/sensor-api/current`（Vite 代理转发） |
| 代理配置 | `FrontEnd/Intelligent_meeting_cloud/vite.config.js:40-44`：`/sensor-api` → `target: http://127.0.0.1:5000`，`rewrite: ^/sensor-api → /api` |
| 前端请求封装 | `src/apis/sensor.js:3-15`：`axios.create({ baseURL: '/sensor-api', timeout: 5000 })`，`getCurrentSensorData()` → `GET /current` |
| 3D 组件 | `src/views/User/Room3D/index.vue`（Three.js，Vue3 `<script setup>`） |
| 拉取周期 | 3000 ms（`index.vue:1040` `window.setInterval(refreshSensorData, 3000)`） |
| 首次拉取 | `index.vue:1039` 挂载时立即 `refreshSensorData()`，随后进入轮询 |

**结论：3D 场景的显示值全部来自 `/api/current` 的响应体，组件内不存在“设备状态写死数组”。**
唯一内置的是**界面兜底默认值**（`index.vue:15-31`，仅在请求发出前/失败时使用），这是缺陷 D-02 的根源，见第 7-8 周《交互与异常提示说明》第四节。

## 二、4 类状态 → 字段 → 3D 对象属性

### 2.1 人员（occupancy）

| 接口字段 | 类型 | 取值 | 前端派生 | 3D 对象/属性 | 代码位置 |
| --- | --- | --- | --- | --- | --- |
| `motion` | boolean | true / false | `occupied = motion \|\| presence` | 人形模型组显隐 | `index.vue:155`、`849-851` |
| `presence` | boolean | true / false | 同上（`data.presence ?? data.devices?.presence`） | 同上 | `index.vue:882`、`849-851` |
| `people_count` | number | 0..N | `count = min(8, max(1, people_count))`，无人时归 0 | 最多同时显示 8 个人形模型（`person.visible = occupied && index < count`） | `index.vue:156-162`、`849-851` |

> **注意（实测差异，缺陷 D-09）**：接口 `/api/current` **没有** `people_count` 字段（只有 `motion_count` 累计次数）。前端取值链为 `Number(data.people_count ?? data.occupancy ?? (occupied ? 1 : 0))`，因此**只要有人就恒为 1**，8 个人形只会出现 1 个。判定：人数维度目前只能表达“有/无人”，不能表达“几个人”。修法二选一：① 接口补 `people_count`（由 PIR 计数或多目标检测给出）；② 前端改读 `motion_count` 并按段落差分估算（不严谨，仅演示）。建议选 ① 并写进 `api-v1.0` 的兼容新增字段。

- 人形模型：`liveObjects.people` 数组，动画上下浮动（`index.vue:985-987`，`position.y = sin(t*2+i)*0.025`）。
- 界面文字：统一状态对象面板「人员 / 无人 / N人」（`index.vue:1089-1092` 区域）。

### 2.2 门（door_status）

| 接口字段 | 类型 | 取值 | 前端派生 | 3D 对象/属性 | 代码位置 |
| --- | --- | --- | --- | --- | --- |
| `door_open` | boolean | true / false | `door.open`（本地点击后由 `doorOverride` 临时优先） | 门扇绕门轴旋转：`rotation.y = open ? -Math.PI*0.52 : 0` | `index.vue:489`、`852-854` |
| `door_source` | string | `hardware` / `room-3d` / `week7-verify` … | `door.source`，界面显示「门状态来源：传感器同步 / 本地演示」 | 门上方状态灯颜色与自发光强度 | `index.vue:165-168`、`855-860` |

- 门模型：门框 + 门扇（轴心在门轴，`openRotation = -Math.PI * 0.52` ≈ 93.6°），点击门扇可通过射线拾取直接开门/关门（`index.vue:972-978`）。
- 门状态灯：`doorBeacon`，开=绿(0x22c55e) 强度 0.95，关=橙(0xf59e0b) 强度 0.42（`index.vue:855-860`）。

### 2.3 温湿度（climate）

| 接口字段 | 类型 | 单位 | 前端派生 | 3D/界面表现 | 代码位置 |
| --- | --- | --- | --- | --- | --- |
| `temperature` | number | ℃ | `climate.temperature` | ① 环境指示牌（`dhtIndicator`）颜色 ② 空调模块（`hvac`）冷/热自发光 ③ 顶部「环境」数值 | `index.vue:170`、`803-808`、`817-822` |
| `humidity` | number | % | `climate.humidity` | ① 加湿器模块（`humidifier`）干/湿自发光 ② 顶部「环境」数值 | `index.vue:171`、`810-815` |
| `temp_min` / `temp_max` | number | ℃ | **未使用**（界面硬编码 28/18 判越界） | — | 缺陷 D-06，见下 |
| `humidity_min` / `humidity_max` | number | % | **未使用**（界面硬编码 68/35 判越界） | — | 缺陷 D-06 |

- 当前代码的判据（`index.vue:794-797`）：`hot = temp >= 28`、`cold = temp <= 18`、`dry = humidity <= 35`、`wet = humidity >= 68`。
- 接口返回的阈值（实测）：`temp_min=20, temp_max=26, humidity_min=40, humidity_max=60`。
- **两者口径不一致**：接口说 26℃ 以上就该提示，界面要到 28℃ 才变蓝；接口说湿度 60% 以上越界，界面要到 68% 才变灰。已登记为 D-06，修复方案见第 9-11 周《缺陷跟踪表》。

## 四、与「统一状态对象」的字段差异与处理

第 3 周约定的统一状态对象（`week5/mock/state.json`）使用：

| 统一对象字段 | 3D 实际读取字段 | 差异处理 |
| --- | --- | --- |
| `room_id` | 无（前端按 `activeRoomId` 本地三间：executive/training/creative） | 3D 与房间业务未打通，D-05 |
| `occupancy` | `motion` / `presence` / `people_count` | 兼容读取，但语义重叠；`people_count` 接口未下发 → 人数退化为 0/1，D-09 |
| `door_status: "open"/"closed"` | `door_open: true/false` | **字段名与类型都不一致**，D-05 |
| `devices.alarm` | `smoke >= 60`（前端）/ `smoke >= 100`（后端 `SMOKE_THRESHOLD`） | **报警口径三处不一致**，D-04 |
| `source` / `quality` | 无（前端用 `door_source`、`sensorState`） | 未映射 |

**第 8 周冻结接口时按“接口为准”统一**：以 `/api/current`（`door_open:boolean`）为唯一字段口径，统一状态对象文档同步改为 `door_open`，`door_status` 仅作历史兼容字段保留一个版本周期。

## 六、字段核对脚本

`scripts/verify_state_binding.py` 拉取 `/api/current` 后逐项校验：

- 17 个顶层字段是否齐全、类型是否符合本表；
- `devices` 子字段是否齐全；
- 派生值（`occupied`、`people.count`、`door.open`）是否与字段一致；
- 界面阈值（28/18/35/68/60）与接口阈值（26/20/40/60/100）差异是否被记录。

运行：`python scripts/verify_state_binding.py --base http://127.0.0.1:5000`

输出：`results/状态字段校验结果.json` + 控制台对照表。
